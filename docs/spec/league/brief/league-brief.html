00 · Overview

The league model

Three layers turn "2 RB per team" into 192 individual slots a single sale can remove exactly one of. Every VORP model is ultimately a fill over these slots.

The layers change at different rates. The frozen template holds the rules every seat is bound by — teams, budget, per-seat positions and flex. A generic matching engine answers "given these players and these slots, who's selected," knowing nothing of teams or sales. The seats layer applies the template to real money and real players, and is the only one that mutates — once per sale.

Keeping them separate is what let the seats layer replace a count × teams approximation with real per-team slots without touching the engine at all.

01 · The template

The roster template

Nothing computed — the frozen shape of one team's roster, read from this league's Sleeper settings once, so no downstream model carries its own copy of these numbers.

LeagueConfig is a frozen dataclass: starting slots per position, flex slots and what each accepts, bench spots, plus the league-wide constants. There is no fantasy-standard shape to hardcode — flex types vary (FLEX, REC_FLEX, SUPER_FLEX each accept a different set), and which positions a league plays isn't fixed either. This league never mentions K, so kickers aren't in its template anywhere.

Three derived queries: draftable_positions() unions positions with a starting slot and those any flex accepts; flex_peers(pos) returns every position that could take a flex slot away from it; roster_size sums concrete + flex + bench (16 here). The template has no concept of a sale — every mid-draft question is answered downstream.

02 · The engine

Slot assignment

A generic bipartite match: players in, slots in, an optimal fill out. It doesn't know what a team, a seat, or a sale is — three callers each hand it a different pool.

Taking the top N at each position is wrong because flex slots are shared — a strong TE class can pull SUPER_FLEX slots off running backs, and a per-position count can't express that. A greedy fill (concrete, then flex, then bench) is order-dependent. So it uses Kuhn's algorithm: players processed points-descending, each seated via an augmenting path that can bump an occupant into its other eligible slot. assign_to_slots returns the full slot→player mapping; solve_optimal_fill drops slot ids; summarize_by_position gives, per position, how many cleared and the points of the best one who didn't.

Full spec: docs/spec/league/02-slot-assignment.md.

What the spec pins down

  • ✓ A contested SUPER_FLEX goes to whichever position has the better player, with no explicit rule saying so — it falls out of the matching.
  • ✓ The same function runs over 192 league-wide slots or 16 for one seat — it's the same code, and cost scales with the pool it's handed.
  • ✗ A short pool sets pool_exhausted=True and level_points=None — not a bar of 0, since there's no baseline to read.
03 · The substrate

Seats and sales

Real teams holding real money and players, so a single sale is expressible — 192 → 191 slots, not the 192 → 180 a per-team count would force.

A Seat per team holds its remaining budget and bought players; LeagueState pairs the seats with the one shared template and applies it per seat to generate slots on demand. From that it answers the three questions the models need: the open slots (every seat's unfilled spots unioned into one flat list — exactly what solve_optimal_fill takes), the pool (Σ remaining budgets), and spots left. Each sale removes exactly one slot from the union and its price from the pool.

Per seat it also reports a max_bid of budget_left − (open_slots − 1) × min_bid, reserving $1 for every other open spot so a plan can never leave a seat unable to field a roster. Worked example: seat 4 buys a back for $60, is left with $140 and 15 open spots, so max bid = 140 − 14 = $126.
