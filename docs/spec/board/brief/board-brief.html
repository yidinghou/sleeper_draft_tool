00 · Overview

The live draft board

The surface a manager watches during an auction — a thin renderer over the pricing core that adds no valuation of its own. The browser holds no model.

One Python server, draft_board.py, polls the draft, reprices every remaining player against the money and slots still in the room, and serves a three-slide deck. Every dollar on the page traces back to a price_board solve in that one process; the pricing math itself lives in vorp/07 and the chain below it.

What this module owns is everything around that solve: getting live picks in, deciding who sits where, shaping the /state.json payload, drawing the deck, and letting you scrub back through the draft. The four steps that follow are those four concerns — all one server process.

Full map: docs/spec/board/index.md.
01 · Getting picks in

Live data ingestion

Turn a running auction into the shrinking residual league the pricing core reprices on — polling, accumulating, and cache-busting to paper over what Sleeper won't serve.

Picks arrive three ways, mock-first and switchable at runtime through POST /source with no restart: a local --picks-file re-read on mtime change (the testable path), a polled --draft-id, or an inline paste. In draft mode a cheap /draft poll computes a draft_fingerprint; only when that string changes does it pay for the expensive /picks refetch. The whole draft mirrors to data/draft-<id>.json so history survives a restart and replays offline through the same --picks-file path.

Spec docs/spec/board/01-live-data-ingestion.md.

What the spec pins down

  • ✓ Sleeper exposes only the current high bid, so each observed rung is appended to data/bid-log-<id>.json and the ladder is reconstructed from poll history — a sample of the bidding, not a full transcript.
  • ✓ Adaptive cadence: the poller idles at 0.75s but drops to 0.2s the moment a player is on the block, so a missed raise can't slip by — both localhost-only, so fast is essentially free.
  • ✗ A pick with no draft_slot lands on a synthetic UNKNOWN_SEAT rather than being attributed to seat 0 — the sale still leaves the pool, but no real seat is charged.
02 · Who sits where

Seat identity and divisions

Resolve real managers where Sleeper knows them, fill the rest with a deterministic fiction, and group the twelve seats into divisions — so a mock looks and behaves like the live board before a single real name exists.

Two joins plus a fill. seat_identity maps each seat to a manager from draft.draft_order (authoritative, both array and object shapes handled) and each pick's picked_by (reveals a seat the moment it drafts). random_fill then keeps the real pins and draws league members for every open seat from a pool shuffled by a fixed MOCK_SEED, so a given mock lays out identically every run. build_divisions orders the bands mine-first and returns a display-only column permutation; the per-seat bids arrays stay seat-indexed.

Spec docs/spec/board/02-seat-identity-and-divisions.md.

What the spec pins down

  • ✓ "My seat" is inferred from a configured handle (MY_USERNAME) against both username and display_name, never entered by hand — and left untouched when the handle isn't present yet.
  • ✓ The fill is a no-duplicate deterministic permutation; as the draft seeds, real managers overwrite their placeholders and may reshuffle the other open seats.
  • ✗ The fill is a plausible fiction — names, divisions, and even which seat is "mine" are seeded guesses, provisional until the draft really seeds.
03 · Payload & deck

The rendering contract

One server-side payload, one three-slide deck that renders it and nothing else. Every number on the page is a Python solve — the JavaScript holds no copy of the pricing model.

build_payload runs price_board on the residual league and folds it into named blocks the deck consumes over /state.json. Slide 1 (Live): a worth-blend bar placing up to five dollar figures on a bargain→fair→overpay gradient, per-seat buying-power bars, a draft-state table with draggable "Bar (pts)" sliders, and run-pressure cards. Slide 2 (Market): a sortable pool matrix with a Bargain column and a per-seat bid matrix. Slide 3 (Rosters): division bands whose cards run an in-browser bipartite slot-fill.

Spec docs/spec/board/03-rendering-contract.md.

What the spec pins down

  • ✗ Nothing is modeled in JavaScript — porting even part of the pricing to JS would mean two implementations that drift, so the client reads every figure straight off the payload.
  • ✓ The one client compute, fillSlots, is a deliberate tested mirror of the Python matching — bench slots held out so a QB is never benched to seat a lower WR in SUPER_FLEX.
  • ✓ Display order never touches the data: seat_order reorders which column is drawn where, but bids[sid] still yields each seat's own value.
04 · Scrub the draft

The time-travel scrubber

Replay the board as it stood after any pick and watch the prices move — every frame built at most once, ever, then served from memory and disk.

get_payload_upto(n) replays only the first n picks through the same build path and returns a frozen frame. A full reprice is ~1.5s, and a drag crosses dozens of picks a second, so frames are memoized by a prefix signature — a JSON blob of the schema version, the first n picks as [pick_no, player_id, amount] triples, and the baked seat names. A disk cache at data/frames-<id>/<n>.json and two warmer threads keep frames ready; a pinned scrub bar (Shift+←/→, Esc to snap live) drives it.

Spec docs/spec/board/04-time-travel-scrubber.md.

What the spec pins down

  • ✓ FRAME_SCHEMA_VERSION (currently 8) folds into the signature, so a bump invalidates every persisted frame at once — a cache invalidation, not a manual purge.
  • ✓ A miss takes a build lock, double-checks the cache, builds once, and stores; per-request fields (my_seat, view, the just-sold block) are re-stamped onto a copy so the cached body is never mutated.
  • ✗ A scrubbed "on the block" is the pick's winner shown as sold, never the live bidding — Sleeper never exposes past nominations, so the historical timeline is only as complete as the recorded ladder.
