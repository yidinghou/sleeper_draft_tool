00 · Orientation

The build order

Everything on this branch prices a player against the money and slots actually left in the room. Rebuild it in dependency order and each layer stands on a finished one below it.

data ─▶ league ─▶ vorp ─┬─▶ board ─▶ analysis └─▶ publishing

The arrow runs one way. Data feeds the engine; the engine feeds the board and the pages; the analysis tools read what the board writes. Build against the arrow and nothing has its inputs yet.

Each of the six modules that follow is a self-contained step: FAQ specs saying what each piece computes and why, a guide.md saying how to rebuild it with the exact commands, and a condensed brief like this one.

Full map with links: docs/spec/index.md.
01 · Data first

The data pipeline

Every dollar and every VORP figure rests on two CSVs. Build them before any model runs, or there is nothing to price.

Two TypeScript exports fetch live feeds, join a hand-scraped snapshot, and write flat CSVs into data/. projections-{season}.csv is load-bearing — it fuses the Sleeper player dump, season and weeks-1–3 projections, and the scraped draft board into one row per player, with a pts_source flag preferring the board number over the API. boberto-{season}.csv is the second opinion: an independent FantasyPros projection plus real market AAV, matched back onto Sleeper ids.

Specs data/01-projections-export.md, 02-boberto-twin.md · rebuild data/guide.md.

What the specs pin down

  • ✓ The board's $/rank/points stay one consistent snapshot; API points only fill players the board is missing.
  • ✓ The Boberto feed is matched by normalized name + position, team tie-break, DEF-by-team, name-only fallback — no invented matches.
  • ✗ sleeper_proj_dollar is not API-available — it is client-side only and must be hand-scraped, which is why the board CSV is committed.
02 · The substrate

The league model

Turn "2 RB per team" into 192 individual slots a single sale can remove one of. Every VORP model is ultimately a fill over these slots.

Three layers that change at different rates: the frozen template (teams, budget, per-seat slots including flex), a generic bipartite matching engine that answers "given these players and these slots, who's selected," and the seats layer holding real money and real players — the only layer that mutates, once per sale.

Specs league/01-roster-template.md → 03-seats-and-sales.md · rebuild league/guide.md.

What the specs pin down

  • ✓ Flex eligibility is baked into slots, so a contested SUPER_FLEX goes to whichever position has the better player this year.
  • ✓ max_bid reserves $1 for every other open slot, so a plan can never leave a seat unable to field a roster.
  • ✓ A sale consumes exactly one slot at the buying seat — the operation the whole residual-repricing story needs.
03 · The engine

The VORP engine

A player is worth the points he adds above the last freely-available player at his position — re-solved against the league that is actually left.

The chain: replacement level (01) and value-over-last-rostered (02) from one league-wide optimal fill; two whole-budget lenses side by side (03); the shipped blended-bar price on one dial (04); a principles harness that judges every model against named laws (05); the same price re-solved on every sale (07); one seat's own value once its roster is known (08); and the best affordable roster its money can still buy (09), plus a seeded price-scenario version (09b).

Specs vorp/01…09b · rebuild vorp/guide.md · deep dive vorp/brief/vorp-brief.html.

What the specs pin down

  • ✓ VORP is floored at zero — nobody is worth less than the freely-available option.
  • ✓ Prices reconcile: they sum to exactly teams × budget − spent.
  • ✗ The affordable-roster solve is greedy, not the exact knapsack — exact only on flat prices, within a tight bound otherwise (the tests pin both).
04 · The surface

The live draft board

A single Python server polls the draft, reprices everyone left, and serves a three-slide deck — and adds no valuation of its own. The browser holds no model.

Picks arrive three ways (local mock file, polled Sleeper draft, inline paste) and become a residual LeagueState. Seat identity resolves real managers where Sleeper knows them and deterministic placeholders where it doesn't, then groups seats into divisions. The /state.json payload drives the deck; the scrubber replays any prefix of the draft as a memoized frame.

Specs board/01…04 · rebuild board/guide.md. Runs on vorp/07.

What the specs pin down

  • ✓ Sleeper exposes only the current high bid, so each observed bid is appended and the full ladder is rebuilt from poll history.
  • ✓ Scrub frames are memoized by a prefix signature and a FRAME_SCHEMA_VERSION; a schema bump invalidates the disk cache.
  • ✗ Nothing is modeled in JavaScript — every number on the page is a price_board solve from the one Python process.
05 · The exhaust

Draft-trend analysis

Read a draft after it happens: walk the bid ladder once and label each seat against the room's own medians. Descriptive, not prescriptive — no model in the loop.

Per seat: wins, spend, bids, distinct auctions entered, win-rate, nominations, positional spend, max bid — then a field-relative behavioral read (efficient closer, volume accumulator, heavy nominator, pays-up / bargain buyer, position-concentrated, selective). It reads the bid log the board's ingestion reconstructs.

Spec analysis/01-bid-trends.md · rebuild analysis/guide.md. Forward-looking counterpart: vorp/09b.

What the specs pin down

  • ✓ Labels are thresholds against the room's medians (e.g. efficient closer at win-rate ≥ 1.25× median), so they shift with the field.
  • ✓ Deterministic per file snapshot — same input, byte-identical output.
  • ✗ A live draft file grows as picks come in, so each run is a snapshot in time, not a final verdict.
06 · The shareable

HTML publishing

Turn a Python model into a self-contained page whose JavaScript re-solves in the browser — exported as both a standalone local file and an optional Artifact fragment.

write_pair writes both from one fragment string: a standalone pages/ page wrapped in a minimal skeleton, and a gitignored artifacts/ fragment for a host that supplies its own skeleton. The whole concern is keeping the browser port faithful to the model — the seat-value build re-solves every preset in Python, and the auction-drift demo asserts its template-extraction anchors before it merges four scenarios into one page.

Specs publishing/01-html-export-pipeline.md, 02-auction-drift-demo.md · rebuild publishing/guide.md.

What the specs pin down

  • ✓ The standalone page renders in standards mode from a file:// URL — the copy opened on a phone.
  • ✓ The auction-drift build hoists the shared opening board out of four payloads to keep the file near single-scenario size.
  • ✗ --verify re-solves the presets in Python and prints them; it does not itself diff against the shipped JavaScript.
